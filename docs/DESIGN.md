# Project Design Reference
*Open source government contracting business development intelligence ecosystem - design elements, constraints, and decisions*\
*Status: living document; §8 mirrors `src/orrery/migrations/`. Last updated: 2026-09-14*

---

## 1. Mission

Build a free, open source ecosystem for U.S. federal business development intelligence, aggregating, searching, and analyzing public government spending and opportunity data, that is free to self-host and community-owned. Incumbent tools are priced for enterprise budgets, well beyond the reach of the small businesses that make up most of the market; a free, self-hosted alternative is structurally hard to answer without giving up that pricing.

The ambition is not a better SAM.gov search. The ambition is an entity graph of agencies, offices, contractors, contracts, and officials, onto which opportunity data, award history, entity registrations, budgets, economic indicators, technology developments, and the user's own company profile are all resolved. The product is the context view over that graph: an opportunity page that already knows the incumbent, the contract history, the contracting officer's other awards, the agency's budget line, and the protest record.

**This is a movement, not a competitor.** The disruption comes from being structurally unanswerable: nobody can compete with free + self-hosted + community-owned without destroying their own business model.

## 2. Core principles (the non-negotiables)

1. **Shipped code stays free and forkable.** Guaranteed by a permissive license, not by a pricing page.
2. **Self-hostable by design.** One `docker compose` command on a home server or cheap cloud box (`run` today; `up` once the ingestion daemon makes a long-running service, §5).
3. **Zero telemetry.** The software phones home to nobody. In a user base that works near sensitive programs, this is a headline feature.
4. **Bring your own keys.** Users supply their own SAM.gov API key and LLM credentials. The project never touches credentials, billing, or inference costs.
5. **Model-agnostic AI.** All AI features talk to a configurable OpenAI-compatible endpoint. Local (Ollama/Qwen-class) or frontier cloud (Claude/GPT) - user's choice.
6. **No hosted service in v1.** No accounts, no uptime obligation, no support burden while the project is young.
7. **Public data + public knowledge only.** FAR mechanics, Shipley-style methodology, protest case law: fair game. Proprietary capture intelligence, customer relationships, or any organization's internal process: never enters the repo.
8. **People appear only in their official public capacity.** Contracting officers, program managers, and agency leadership are covered from government sources (award records, the Federal Register, agency org charts, official bios) and only in the roles those sources document. No scraping of personal social media, no profiling beyond the public role. This is the first question a defense-adjacent reviewer will ask, so it is answered here.
9. **Every fact carries provenance.** Anything the system asserts about an entity records where it came from, when it was observed, and how confident the extraction was. A fact without a source is not stored. This is what makes LLM extraction and community-contributed sources safe to build on.

## 3. Strategic decisions

- **v1 thesis: semantic search *inside* solicitation documents, for a narrow slice.** SAM.gov already offers keyword search and free saved-search email alerts over notice metadata; a self-hosted copy of that is not worth a Docker install and an API key. What SAM.gov cannot do is search the attached solicitation documents themselves including the statements of work, Section L/M instructions, and amendments where the real signal lives. Notice metadata and descriptions come through the quota-bound API, while the attachment files themselves are served without a key (§5), so v1 goes deep on a user-chosen slice rather than wide across all of SAM.gov, and the depth comes from attachment text. The slice is `ORRERY_NAICS` and nothing else: a list of two-to-six-digit prefixes matched against the NAICS code the government put on the notice, so `5415` takes the whole industry group and `54` the whole sector. It bounds how much is ingested; it does not judge whether a notice is worth pursuing, and no agency filter narrows ingestion (agency prefixes are a search and saved-search filter, over notices already in the store). "Mirror SAM.gov, then add search" is explicitly rejected.
- **The entity graph is the foundation, from the first migration.** The schema is entity-centric, not opportunity-centric. Notices are one event stream among many that resolve onto shared identities for agencies, offices, contractors, contracts, and officials. v1 populates the graph only from SAM.gov and resolves identities only by exact keys (agency path codes, UEI, CAGE, PIID), but the tables, the provenance model, and the resolver interface exist from day one so that no later source forces a reshape.
- **Small core, everything else is an adapter.** The core is the graph, the ingestion framework, and the query surface (one query module that the terminal UI, the CLI, and the MCP server all sit on). Every data source is a self-contained adapter that produces raw documents, resolved entities, and sourced facts. This is the only way a solo maintainer carries the terminal ambition, and it is what makes each new source a well-bounded community contribution.
- **License: Apache-2.0.** Permissive, with an explicit patent grant. Chosen so that corporate and defense-adjacent legal review does not block adoption, and so the project can be the substrate other tools build on. Copyleft (AGPL) was considered and rejected: it gives reciprocity, not exclusivity, and it deters exactly the organizations the project wants as users. Closed forks by others are an accepted cost; the maintainers and community are the moat, not the license.
- **Contributions under DCO.** Contributors sign off that they have the right to submit their work. No CLA: the core will never need relicensing, and copyright stays with the people who wrote the code.
- **No commercial plans.** No paid tier, hosted service, or revenue is planned. The architecture (public/private data boundary, versioned interfaces) leaves commercial add-ons *possible* without committing to them.
- **Engine first, in the open, self-hosted.** A hosted deployment of the same engine is a possible phase-two *deployment decision*, not a rewrite. The first year of work is identical in both futures.
- **Design for hosted from day one, without hosting.** Multi-user-aware data model even while v1 runs single-user. Clean boundary between engine and interface: every front end goes through the same query module, so a hosted deployment changes where the engine runs, not how it is asked questions.
- **Terminal-forward interface.** The primary interface is a full-screen terminal UI in the idiom of system monitors such as btop: boxed panels, dense tables, keyboard-driven, live, and drawn in the terminal's own palette. It is built with Textual, in the same language as the engine, and the identical app is served in a browser tab for anyone who does not live in a terminal. This is a deliberate trade: it narrows first adoption to technical users in exchange for an interface a solo maintainer can build and keep excellent, and it bets that dashboards for everyone else are built by the community on the substrate below. No bespoke web UI is planned; Datasette over the SQLite file is the point-and-click table browser.
- **Setup and every operation live inside the app.** Nothing requires editing a file or running a command outside `orrery top`: settings are a form that writes `.env` (the one configuration store, so Docker, scripts, and the CLI see the same values; real environment variables override it and show as locked), the profile, workflow, and saved searches are forms over the same TOML documents, and every long-running operation is a job with a log. `$EDITOR`, `--file`, and the CLI remain for scripts. Decided 2026-09-07.
- **Wedge market:** small businesses chasing set-asides who will never pay enterprise prices for BD intelligence. Build for them.

## 4. Architecture shape

- **Small boring core:** a data daemon that ingests public sources into a local store. Small enough that a single part-time maintainer can keep it healthy.
- **Entity graph and provenance layer:** the spine of the store (§8). Entities carry their natural keys and aliases; facts about them are append-only rows that name their source, observation time, and confidence. Resolution in v1 is exact-key matching; fuzzy and LLM-assisted resolution arrive later behind the same interface, and every resolution decision is itself a sourced fact so it can be audited and reversed.
- **Source adapters:** one per data source, each responsible for fetching, quota accounting, raw storage, typed parsing, entity resolution, and fact emission for that source alone. Adapters are versioned, register themselves in a `sources` table, and never write outside the tables the framework hands them. In v1 the adapters are the three SAM.gov ones (notices, bulk extracts, entity registrations) and USAspending awards, and they ship inside the core; the adapter interface is what the v2 plugin interface is built on.
- **Context view as the product:** the terminal UI and MCP surface are organized around entities, not tables. Pull up an opportunity and see the agency, the incumbent, the award history, the officials involved, and the budget context, each fact linked to its source. Search and alerts feed this view; they are not the product by themselves.
- **Four surfaces over one query module.** (1) `orrery top`, the terminal UI (`src/orrery/tui/`, Textual, drawn in the terminal's own palette): a dashboard of quota spent against budget with a 30-day sparkline, the fetch queues, store activity with a 14-day sparkline, then this week's work on the shop's own calendar (every task due, whatever its subject, and response deadlines for pursuits in a gated stage), what needs attention (gate ready, hold due, stalled) with the open pursuits per stage, and the government's dates for the next 60 days as a secondary strip (key `1`); an opportunities table with keyword search over notice and attachment text (`2`, `/`), one row per solicitation with its furthest-along notice standing for the group and awards hidden behind `a`; the pursuits board by stage and the pursuit screen with its tasks, notices, and decision log (`3`; keys for done, task, gate, back, outcome, PWin, notes, office, incumbent, and `x` to accept the latest assessment's suggested tasks); `t` on the dashboard adds a task about anything, or about nothing; the recompete radar (`4`, `p` starts a pursuit with the award as incumbent); the context view of one notice with its agency chain, its pursuit, incumbent, description, the office's award history in the notice's NAICS, the government contacts it names, and documents (`t` opens or starts its pursuit, `a` opens the office, `i` opens the incumbent, Enter on an award opens its vendor, `o` opens the SAM.gov page); the entity view (chain, offices, awards made or won, registration facts, recent notices; Enter on an award crosses to the other party); and setup (`5`; `j` opens its Jobs tab from anywhere): Connections over every `ORRERY_*` setting (`ctrl+s` writes `.env` through `src/orrery/dotenv.py`, `ctrl+t` probes the focused field's service with the smallest request), Profile, Workflow, Searches, and Jobs. `orrery top --serve` puts the same app in a browser tab. Long-running operations are a registry (`src/orrery/jobs.py`: needs, parameters, run, one-line summary) that the CLI and the app both call; the app runs one at a time in a thread on its own connection, with cooperative cancellation between pages, batches, and items (`src/orrery/progress.py`), and a cancelled run closes `failed` with the error `cancelled`. (2) The CLI, where every command that prints data takes `--json` from the first such command (§9 step 3), so it composes in scripts. (3) The MCP server. (4) Documented read-only SQL views, named `v_*`, with a stability promise, so community dashboards (Datasette, Grafana's SQLite plugin, a shell script, an AI agent) survive migrations of the underlying tables. The views and the MCP tools are versioned together; the raw tables are not a public interface.
- **Quota-aware fetch pipeline.** Every search page and every notice description spends SAM.gov API quota (§5); attachment files are served from public URLs without a key. The pipeline is therefore a priority queue with accounting, not a crawler: keyed requests are logged against the day's budget and the daemon stops before the quota does, while attachment downloads are rate-limited only out of politeness and prioritized by the user's slice and saved searches. Text extraction and embedding happen after fetch and never spend quota; the only other hosts ever contacted are USAspending (awards, no key) and the embedding endpoint the user configured. In v1 the queue is `orrery fetch`: descriptions first, notices matching any saved search's filters first, then soonest `response_deadline` (undated last) then newest posting, stopping when the day's budget is spent; then attachments in the same order with a `ORRERY_FETCH_DELAY` pause (default 1 s) between downloads. Failures are recorded and not retried, in that run or automatically in later ones.
- **MCP server from day one:** the whole store is exposed via MCP so any AI agent can sit on top. Goal: become the substrate the next wave of tools builds on. In v1 this is the *only* extension surface (the CLI's JSON output and the read-only SQL views are integration points, not extension points); the MCP interface is versioned from the first release. Interface version 1 (`orrery mcp`, stdio only, the client spawns the process) exposes `search`, `notice`, `entity`, `upcoming`, `pipeline`, `track`, `history`, `saved_searches`, `run_saved_search`, `save_search`, `queue_status`, `quota_today`, `profile`, `awards`, `contractor`, `recompetes`, `pursuits`, `pursuit`, `new_pursuit`, `link_notice`, `gate`, `tasks`, `task_done`, `update_pursuit`, and `assessments` (stored assessments only; the server never contacts a model), each a thin wrapper over the query and workspace modules returning the engine's own records. Tools and their fields are only ever added. Nothing an agent can call spends SAM.gov quota or contacts the network: ingest, fetch, and embed are deliberately not tools, and the only writes are tracking, saving a search, and marking a task done. There is no tool that creates a task: an agent minting work with no rule behind it is the flood the alert design exists to prevent, and tools are only ever added, so one can arrive when there is a rule.
- **Capability-scoped plugins in v2, not v1.** The core loads no third-party code in v1. When a plugin interface arrives, each plugin declares which tables it reads and writes and whether it needs network access; the core enforces the declaration and shows it at install time. The community-value areas (agency forecast scrapers, enrichment adapters, capture skills, compliance matrix generators, PWin models) arrive through that scoped interface or as MCP-driven agents, never as unreviewed code with access to a user's pipeline.
- **Storage: SQLite.** Single file, zero admin, sufficient for a single-team BD workbench. FTS5 for full-text search; sqlite-vec for embeddings, as a plain table of float32 blobs ranked by its scalar `vec_distance_cosine()` (brute force is well under a second at v1 sizes; the `vec0` virtual table is the upgrade path if a store ever outgrows that). A graph in SQLite is just tables with foreign keys. If cross-source analytics ever outgrow it, an analytical sidecar (DuckDB over the same files) comes before any change of primary store; revisit the primary store only if a hosted multi-tenant phase arrives.
- **Deployment: Docker Compose.** Install is one command. Installation path must be transparent and auditable (defense-adjacent IT will read before running). Images are built from the repo's own Dockerfile, and a documented build-from-source path with no registry pull is a first-class install route, not an afterthought. In v1 there is no daemon, so the invocation is `docker compose run --rm orrery <command>` against `compose.yaml`; `docker compose up` becomes meaningful when the ingestion daemon arrives.
- **AI task tiering:** high-volume grunt work (classification, extraction, tagging, summarization, embeddings, fact extraction) targets small local models; heavy reasoning (proposal analysis, Section L/M work, PWin judgment, fit and gap analysis against the company profile) targets frontier models via user's key. In code this is two slots behind one interface (`src/orrery/ai/`): `fast` (default: a local Ollama through the OpenAI-compatible chat shape that Ollama, LM Studio, llama.cpp, vLLM, OpenAI, and OpenRouter share) and `deep` (optional; Anthropic through its official SDK with JSON-schema structured output, adaptive thinking, and server-side refusal fallbacks; or any OpenAI-compatible service), configured under `ORRERY_AI_*`; the deep slot is the fast slot until one is set. The first task is the pursuit assessment (`src/orrery/assess.py`, `orrery pursuit assess`): the profile document, the pursuit, its linked notices and the best-matching extracted documents, the incumbent's award and registration facts, and the office's award history go in, bounded by the slot's character budget; a validated verdict (fit and reasons, gaps, incumbent standing, competition, a recommended gate decision with rationale, open questions, suggested tasks) comes out and is stored append-only with provenance (§8 `assessments`). The second task, on the fast slot, is the notice summary (`src/orrery/summaries.py`, `orrery summarize`): a notice's title, typed fields, and description go in, bounded by the budget; a two-sentence summary, a work type from a fixed list, keywords, and the set-aside the text itself states come out, stored once per notice per model and prompt version (§8 `notice_summaries`) and shown in the opportunities table and the context view. No profile goes in, so a summary serves every profile; the set-aside fit against the company profile is derived at read time from the notice's code, the stated one, and the profile's size and set-aside codes. Next on the fast slot: fact extraction into `facts` with the model recorded.

## 5. Data sources (priority order)

Each source is an adapter (§4) and is described by what it contributes to the graph. Everything here is public data; the user's own company is a private input and lives in the workspace layer (§8).

1. **SAM.gov Get Opportunities API (v2):** Active solicitations, sources sought and presolicitations on the day they post, with their attachment links (`resourceLinks`). The *same-day* source: what a key buys is freshness and the notice descriptions, not access to the corpus, since source 2 carries everything older than the current day and attachments are reachable without a key (below). Free key from a SAM.gov account, and optional -- orrery runs without one. Graph contribution: notices as events, agency and office entities from the agency path codes, and the solicitation documents themselves. The API quota is the binding constraint on the whole search layer. Verified against GSA documentation and secondary sources on 2026-09-03 and against the live API on 2026-09-06 (`docs/notes/sam-api-probe.md`); re-verify before first release:

   | Limit | Value |
   |---|---|
   | Date range per request | 1 year max |
   | Records per page | 1,000 max |
   | Personal key, no SAM.gov role | ~10 requests/day |
   | Personal key with a role on an active entity registration | ~1,000 requests/day |
   | Federal system account | ~10,000 requests/day |
   | Notice description | one keyed request per notice (the search response carries a URL, not text) |
   | Attachment download | no key; served from public `sam.gov` file URLs and not counted |

   A notice therefore costs its share of one search page plus one description request, and its attachments cost nothing against the quota: ~1,000 requests/day covers several hundred notices' descriptions, and ~10/day covers one search page and a handful of descriptions. Description fetching is lazy, prioritized, and accounted for (§4, §8); the bulk extracts (source 2) carry descriptions as plain text and are the description source of record for history, which is never backfilled through this API. The API returns no quota or rate-limit headers, so accounting is local.

   **First-run consequence of bring-your-own-key:** nothing about setup waits on SAM.gov. A store built from the bulk extract carries notices and their descriptions, and the attachment manifest and the files themselves are read from public URLs that take no key, so an install with no SAM.gov account at all is a supported path and the README describes it first. A key adds same-day notices; a key with a role on an entity registration raises ~10 requests/day to ~1,000 and so raises how much same-day traffic is affordable. Neither is a prerequisite. This matters for who the project is for (§3): entity registration can take up to 10 business days and requires a business to register, which an individual doing business development work may not have. Measured 2026-09-09 over one NAICS slice: every notice posted before the current day was present in the active extract, and the only miss was posted after that day's file was generated -- the gap the key closes is latency, not coverage.
2. **SAM.gov Data Services bulk extracts:** A daily CSV of every active contract opportunity (about 245 MB and 70,000 rows, verified 2026-09-06) and one archive CSV per fiscal year, published at `sam.gov/api/prod/fileextractservices/.../Contract Opportunities/` and served from S3. No key and no quota. cp1252, 47 columns, quoted fields; descriptions are inline plain text, apparently capped near 32,000 characters; the rows carry no attachment links -- those are read separately and without a key from the manifest endpoint SAM.gov's own web interface uses (`docs/notes/sam-manifest-probe.md`), so a store built entirely from this file still gets the solicitation documents -- and the agency appears as department, sub-tier, and office codes (`CGAC`, `FPDS Code`, `AAC Code`) with their names rather than a path string. This is the primary notice source and the history path, and the only one an install with no SAM.gov account has: `orrery ingest bulk` streams the file and writes the rows in the configured NAICS slice (§7: never a wholesale mirror) as notices with their descriptions already in place, so they never spend a keyed request, and their attachments are then discovered from the manifest and downloaded, both without a key. The API returns descriptions as HTML and the extracts as plain text; both are stored as plain text (§8), and each notice row records which source last wrote it. On overlap the API row wins: the extract only confirms it and fills a description the API has not fetched.
3. **SAM.gov entity registrations:** The public monthly extract (`GET /data-services/v1/extracts`, one keyed request for a 147 MB zip of every active registrant and those expired in the last six months, 142 pipe-delimited fields) and the Entity Management API v3 (`GET /entity-information/v3/entities?ueiSAM=…`, up to ten registrants per keyed request) give UEI, CAGE, legal and DBA names, registration status and expiry, entity structure, business and SBA types, NAICS and PSC lists, and addresses. Both count against the same daily budget as the opportunities API. Verified on 2026-09-07 (`docs/notes/awards-and-entities-probe.md`). Phase 2, after source 4. Graph contribution: the contractor entity spine and the canonical keys that every award and opportunity source resolves against; registration attributes are facts on the contractor, never columns. Only the slice is read from the extract: registrants already in the graph, registrants whose primary NAICS is configured, and the user's own company. Points of contact in registrations are vendor employees and are never stored.
4. **USAspending / FPDS:** Award summaries with PIID, awarding agency, sub-agency, and office code, vendor UEI and CAGE, solicitation identifier, NAICS, PSC, set-aside, competition, values, and period of performance. No key and no quota. Phase 2, built before source 3 (decided 2026-09-07: the award download alone creates contractor entities keyed by UEI and delivers the incumbent and award history; registrations enrich them). Verified against the live API on 2026-09-07 (`docs/notes/awards-and-entities-probe.md`). Graph contribution: contract entities, award events, agency-to-vendor edges. The award download (`POST /api/v2/download/awards/`, a filtered CSV prepared asynchronously) is the only path that carries the awarding office code, which is the same code that ends a SAM.gov agency path; awards resolve to offices by that code alone, because USAspending's top-tier codes are not SAM.gov's CGAC codes for Department of Defense components. USAspending names no contracting officer, so officials come from source 1's points of contact; vendor phone numbers and compensated-officer columns are dropped before storage (principle 8). Full USAspending is very large; the adapter ingests the configured NAICS slice for a date window, and later the slices saved searches and tracked entities imply.
5. **Officials and organizations:** The Federal Register, agency org charts and leadership pages, and GAO bid-protest decisions. Phase 2 to 3. Graph contribution: people in official roles, organizational structure and change over time, protest history per agency and vendor. Governed by principle 8.
6. **Budget and appropriations:** Budget justifications (J-books), appropriations bills and reports, agency spending plans. Phase 3. Graph contribution: budget-line facts attached to agencies and programs, which is the layer incumbent analysts sell. Mostly PDF; depends on the document extraction pipeline built for attachments.
7. **Agency long-range forecasts:** Scattered, non-standard agency sites. v2 territory: community adapters via the capability-scoped plugin interface, or MCP-driven agents. Graph contribution: forward-looking opportunity events before they reach SAM.gov.
8. **Economic and technology context:** Public economic series (FRED, BLS), SBIR/STTR awards, agency technology roadmaps and RFIs, and public news. Later phases. Graph contribution: time-series facts on agencies and NAICS sectors, and technology-trend facts that enrich fit analysis. News is the least structured and most extraction-dependent; it arrives last and only through adapters that honor provenance.

**Known gap: GSA eBuy.** eBuy is the quoting system attached to the GSA Multiple Award Schedule. A request for quote posted there is visible only to schedule holders whose contracts carry a matching Special Item Number, and most of that traffic never reaches SAM.gov: no presolicitation, no sources sought, a lifecycle compressed into days rather than months, and competition limited to the other holders in the SIN. For the wedge market of §3 that is frequently where the winnable work is, so the absence is a real gap and not a rounding error. It is out of scope for v1 because eBuy has no public API. GSA's own tooling reaches it by a manual CSV export from eBuy Open plus browser automation carrying a logged-in session's cookies, and orrery does not automate an authenticated session on a third-party portal or hold the credentials for one: principle 4 leaves credentials with the service they belong to, and the auditable one-command install of §4 does not survive a headless browser driving a government portal as the user. Two things would bring eBuy in. A public API would make it an adapter like any other, quota-accounted the way SAM.gov's is. Short of that, a documented export the user runs themselves and hands to an intake step would let the data in without the software ever holding a login.

## 6. Development workflow

- **AI-assisted, human-steered.** Coding agents do the bulk of implementation; people supply design, taste, and domain judgment.
- **Plan before code, always.** Domain review happens at the plan level.
- **Small commits; git is the undo button.** Commit before every ambitious task.
- **Read every diff; ask until understood.** "Make it simpler" is the highest-value review comment.
- **Tests accompany every feature.** A green suite is the objective check that anyone can trust, regardless of experience.
- `CLAUDE.md` at repo root carries conventions and constraints (this document's principles, condensed) so that agents and contributors share the same rules. Specialized agents as needed: code reviewer, researcher, and a govcon domain expert.

## 7. Explicit non-goals (v1)

- No hosted service, accounts, or billing.
- No customer/tenant management modules.
- No telemetry or usage analytics of any kind.
- No fine-tuned models (skills + retrieval over stock models instead).
- No third-party code loading. The MCP server is the only extension surface.
- No bespoke web UI. The terminal UI served in a browser and Datasette over the database are the web paths.
- No features that require anyone to be on call.
- No wholesale mirror of SAM.gov. v1 ingests the user's configured slice and its attachments.
- No enrichment sources beyond SAM.gov in v1. The graph and provenance tables exist from the first migration; the adapters that fill them from other sources do not.
- No fuzzy entity resolution in v1. Identities resolve by exact keys only; unresolved names are recorded as aliases awaiting a later resolver.

## 8. Draft v1 schema (opportunities engine)

*Mirrors the numbered migrations in `src/orrery/migrations/`. Tables marked (later) are designed but not yet created.*

**Identity and provenance layer (public data, the spine of the graph):**
- `sources`: Registry of adapters: `source_id`, name, adapter version, terms or license of the upstream data, `last_run_at`. Every fact and every ingested row points here. Seeded with `sam_opportunities_api` and `sam_bulk_csv` (0001), `usaspending_awards` (0007), `sam_entities` (0008), and the two reference publishers `census_naics` and `gsa_psc_manual` (0019), whose adapter version is the vintage they ship (`2022`, `2025-04`).
- `entities`: One row per organization or place: `entity_id`, kind (agency / office / contractor / place), canonical name, natural keys where the source provides them (`agency_path_code`, `uei`, `cage`), parent entity, `source_id`, `first_seen_at`, `last_seen_at`. Agencies and offices come from SAM.gov agency path codes in v1: every dot-separated prefix of `fullParentPathCode` is one entity (`agency` for the first segment, `office` below it), keyed by the prefix and linked to its parent, and named by the matching segment of `fullParentPathName` when the two have the same number of segments; otherwise the prefix is the name and the whole name string is recorded as an alias of the leaf for a later resolver to improve. Contractors arrive with source 3. Bulk-extract rows key the office as `CGAC.FPDS.AAC` with the three names as segments, which is byte-identical to the API's key for every three-level organization; a deep Defense hierarchy the API knows under a longer path yields a second, shallow entity for the same office, and the shared last segment (the AAC) plus the shared office-name alias are the merge key for a later resolver. Natural keys are unique where present (SQLite treats nulls as distinct).
- `entity_aliases`: Every name string seen for an entity: alias, `entity_id` (null while unresolved), `source_id`, resolution method (exact_key / manual / fuzzy / llm), confidence, `resolved_at`. Unresolved aliases are the work queue for future resolvers; the schema enforces that `entity_id`, resolution method, and `resolved_at` are null together or set together. A resolved alias is stored once per (entity, alias) pair, enforced by a unique index; unresolved rows are unconstrained because SQLite treats a null `entity_id` as distinct.
- `people`: Officials in their public capacity only (principle 8): `person_id`, name, role title, `entity_id` of the organization, `source_id`, `first_seen_at`, `last_seen_at`. Still empty: USAspending names no contracting officer, so the context view reads the government points of contact straight from each notice's `raw_json` and counts the office's other notices naming them; rows arrive with source 5, when a second source gives a key to link against.
- `contracts`: One row per award, recreated in its final shape by 0007 (no adapter had written the 0001 table): `award_key` (USAspending's `contract_award_unique_key`, unique), `piid` (indexed, not unique: FPDS scopes uniqueness by awarding agency), `parent_piid`, awarding `entity_id` (null while the office is unresolved) with the source's `awarding_office_code` and name kept beside it, vendor `entity_id` (null while unresolved) with `recipient_name`, `recipient_uei`, and `cage` kept beside it, `solicitation_identifier`, award and last-action dates, period of performance (current end, and since 0011 `pop_potential_end`, the end with every option exercised, indexed: the date the recompete radar runs on), current and potential value, NAICS, PSC, award type, set-aside, and extent-competed codes, `source_id`, `first_seen_at`, `last_seen_at`, and `raw_json` (the source row minus vendor contact and compensated-officer columns). Re-sights overwrite the typed columns and `raw_json`; there is no version history yet. Populated by source 4. Resolution rules: the awarding office is the one `office` entity whose `agency_path_code` ends with `.<awarding_office_code>`; when several candidates share the same first two segments (the deep-DoD twin case), the longest path wins; otherwise the office stays unresolved and the office name is recorded as an unresolved alias. The vendor is the `contractor` entity with the same `uei`, created on first sight with the recipient name as a resolved alias, and its `cage` is set only while no other entity holds that CAGE; an award with no UEI stays unresolved with the recipient name as an unresolved alias. Never creates agency or office entities: USAspending's top-tier codes are not SAM.gov CGAC codes for Department of Defense components.
- `entity_registrations`: One row per SAM.gov registration record as observed, added by 0008: `entity_id`, `source_id`, `source_ref` (the extract file name or `api:v3`), `observed_at`, `raw_hash`, and `raw_json` (the public record with every point-of-contact field removed; registrant contacts are vendor employees, principle 8). A new row is written only when the record's hash differs from the latest stored one, so the table is the change history of a registration, the counterpart of `notice_versions`. The typed attributes of a record are facts on the contractor (`sam.legal_business_name`, `sam.dba_name`, `sam.registration_status`, `sam.registration_expires`, `sam.purpose_of_registration`, `sam.entity_structure`, `sam.business_type`, `sam.sba_business_type`, `sam.naics_primary`, `sam.naics`, `sam.psc`, `sam.physical_address`; one fact per list element), never columns on `entities`; an expired registration is a fact, never a deletion.
- `facts`: Append-only assertions about any subject: subject type and id (entity / person / contract / notice), predicate, value (typed as text, number, date, or reference), `source_id`, source reference (URL, document id, or row key), `observed_at`, confidence, extraction method and model where an LLM produced it. The value is stored as text with a `value_type` tag. Facts are never edited; a correction is a new fact with a later `observed_at`, and triggers reject `UPDATE` and `DELETE` on the table.

**Ingestion layer (public data, append-only bias):**
- `notices`: One row per SAM.gov notice: `notice_id` (natural key, unique; an integer rowid `id` exists alongside it because FTS5 external-content and vector tables key on a stable integer rowid), solicitation number, title, notice_type, `full_parent_path_name` and `full_parent_path_code` (the current v2 agency-hierarchy fields; the older `department` / `subtier` / `office` fields are deprecated and are not given typed columns), `agency_entity_id` resolved from the path code, naics_code, psc_code, set_aside_code, posted_at, response_deadline, place_of_performance, active flag, `first_seen_at`, `last_seen_at`, `source_id` (API or bulk extract), description (full text; null until fetched), `description_url` (the URL the v2 search returns instead of text), `description_status` (pending / fetched / failed / none, where none means the search carried no URL; the pending rows are the description fetch queue), `raw_json` (verbatim API payload, or the CSV row as JSON for bulk-sourced rows). On re-sight the typed columns, `last_seen_at`, `active`, `description_url`, `source_id`, and `raw_json` are refreshed; `first_seen_at` and the description text and status are not. `source_id` names the source that last wrote the typed columns and `raw_json`. A bulk-extract row never overwrites an API-sourced notice: it bumps `last_seen_at` and `active` and fills `description` when the status is not `fetched`, which also retires the row from the fetch queue; an absent or bulk-sourced notice gets the full write, and the API overwrites a bulk-sourced row on its next sight. `place_of_performance` is JSON as the source gave it (nested from the API, flat from the extracts). Versions follow one rule for both sources: first sight and every change of the source's own `raw_json`; a bulk confirmation of an API row is not a version, and the API's first sight of a bulk row is one. `description` is plain text whichever source fills it: the API's HTML fragment is reduced to text at fetch time (tags dropped, block elements become line breaks, entities decoded) to match the bulk extracts, so the column has one meaning and FTS never indexes markup; the fragment itself is not kept, and the extracts are the description source of record (§5). A `failed` description is terminal: later runs retry nothing marked failed, so a bad response costs one request, not one per run. `manifest_status` (pending / checked / unknown / failed) and `manifest_checked_at` (0015) are the same idea for the attachment manifest: `checked` means a manifest was read whether or not it named any files, which is what keeps a notice with no attachments from being asked about on every run; `unknown` is SAM.gov answering that it has no such notice and is terminal; `failed` is transient and comes round again under the re-check interval. Since 0017 both stages also record *why*: `description_failure_kind` / `manifest_failure_kind` and the matching `_detail`. The kind is decided where the error is raised rather than by matching a message afterwards, and names the distinctions a retry policy needs -- `gone` (404, permanent), `rate_limited` (429), `server_error` (5xx), `client_error`, `transport` (no response at all), `too_large`, `unknown_notice`, `shape`, `no_url`, `store` (the bytes arrived but would not go to their final path: a name the filesystem will not take, a full or read-only data directory) -- while the detail is the exception's own text, already stripped of the API key. A stage that later succeeds clears both, so a reason never outlives the failure it describes.
- `notice_versions`: Full snapshot on first sight and per detected change; amendments are the norm in this domain, and deadline-change history is itself intelligence. Columns: `notice_id`, `observed_at`, `raw_hash` (sha256 of `raw_json`; a change is detected when the hash differs), `raw_json`.
- `attachments`: Files linked to a notice (solicitation docs, amendments). Rows are created from `resourceLinks` at ingestion time; the file itself is fetched later by the priority queue. Columns: source URL, filename (learned at fetch time), `fetch_status` (pending / fetched / failed / skipped), `fetched_at`, `ingestion_run_id` (the run that fetched the file; null while pending), on-disk `path` relative to the data directory (`attachments/<notice_id>/<sha256[:16]>-<filename>`, so the directory can move; the filename taken from `Content-Disposition` with form-encoded plus signs decoded to spaces, and bounded to 238 bytes -- NAME_MAX less the hash prefix -- keeping the extension, since upstream names run past what the filesystem will store), content hash, extracted text. Unique on (`notice_id`, URL). `fetched_at` and `ingestion_run_id` record the run that last attempted the file, whatever the outcome; `skipped` means it exceeded `ORRERY_MAX_ATTACHMENT_BYTES` (default 100 MiB), and like `failed` it is not retried. `extract_status` (pending / done / unsupported / failed) tracks text extraction, which runs after fetch and spends no quota: the file type is sniffed from its first bytes, never from `Content-Type` (always `application/octet-stream`) or the filename; PDFs are read with pypdf and stored as plain text with pages joined by a form feed, which the FTS tokenizer ignores and which lets a later step recover page numbers by counting separators; Word documents are read with python-docx in document order, paragraphs and tables together, because Section L and M instructions are routinely laid out as tables and a paragraph-only reader would drop the part a bidder needs most; a .docx has no pages, so no separators are written. Workbooks are read with openpyxl, one form-feed block per sheet headed by the sheet's name, so a sheet occupies the position a page would; cached values are read rather than formulas, and only the cells a file actually stores are visited, since these sheets are mostly empty. Other types are `unsupported` until their extractors land, and the run tallies what they were (`pptx`, `ole` for the pre-2007 Office container, `zip`, `rtf`, `html`, `text`, `unknown`), so the summary names the reader a store is missing rather than only counting the files it could not read -- measured over one NAICS slice on 2026-09-09, attachment types ran 70% PDF, 22% .docx and 5% .xlsx, so the three readers cover roughly 97% of files. The workbooks are not the pricing grids the share suggests: the sample held Q&A logs naming whether there is an incumbent, self-scoring worksheets stating how an offer will be evaluated, CLIN structures, and questionnaires. Since 0017 a failed or skipped download also carries `failure_kind` and `failure_detail` on the same vocabulary as the notice stages, so `gone` (the file is not coming back), `rate_limited`, and `too_large` (a cap this install chose) are told apart rather than all reading `failed`. A file that sniffs as a supported type and then will not open is `failed` and, like fetch failures, not retried; one with no extractable text -- a scanned PDF, an empty document -- is `done` with empty text, the queue a later OCR step will read. Since 0015 a row also records how it was found (`discovered_by`: the keyed search's `resourceLinks`, or the unkeyed manifest), the manifest's declared `declared_size` and `mime_type` (so an oversized file is skipped without spending a request and the filename is known before the download rather than after), the stated `access_status` and `export_controlled` flags, `deleted_upstream`, the raw manifest entry, and `last_seen_at` for re-checks. A `resourceLinks` row is a first observation and not the source of record: amendments add files after a notice is ingested, and the search window will not re-see it.
- `ingestion_runs`: One row per adapter run: `source_id`, window queried (posted-from / posted-to), started and finished timestamps, records returned, requests spent (computed from `api_requests` when the run finishes), quota remaining by the local count when the run finished, status (running / succeeded / failed), error text, a resume cursor, and (0014) `filter_json`: the NAICS slice as sent and how many rows each element of it took, so a run that matched nothing says which element came back empty rather than only that the total was zero. (0016) `source_generated_at` is when the file a run read was cut, as the source stated it: the bulk extract is a snapshot taken before the run that reads it, and a run that knows the difference can tell a notice that is genuinely gone from one the keyed API ingested after the cut. It is null whenever the source did not say -- a user-supplied file, a response with no `Last-Modified`. The extract adapter learns it from the `Last-Modified` header and keeps it in a `.meta.json` sidecar beside the downloaded file, so a copy cached earlier the same day still knows its own cut. The awards adapter records its window like the notice adapters; an ingest from a file the user supplied has no window and records none. For bulk runs the cursor is `<sha256 of the file>:<sorted NAICS list>:<rows read>`, written in the same transaction as every batch of rows; a rerun resumes from the latest run with the same file and filter whatever its status, so an interrupted run is a plain rerun, a completed run reads nothing, and a new daily file or a changed NAICS list starts from zero. Every API request is attributed to a run. This is what makes partial backfills resumable and the daily budget reasonable.
- `api_requests`: One row per keyed SAM.gov API request (search pages and descriptions; attachment downloads need no key and are recorded on their `attachments` row instead): `run_id`, endpoint (the URL with the API key parameter stripped; the key is never stored), `notice_id` where the request concerns one notice, HTTP status code (null if no response), response bytes, `requested_at`, error text. `ingestion_runs` keeps aggregate counts; this log is what makes them auditable and is what the daily budget check counts. The row is inserted before the request is sent and updated with the status code and byte count, or the error text, afterwards, so an interrupted or failed request still counts; the budget check counts today's rows by UTC date.
- `naics_codes`, `psc_codes`: Reference tables for clean filtering and joins. Not foreign-key targets: notices carry the codes as plain text so ingestion never depends on reference data being loaded. Agencies are entities, not a separate reference table. Both ship filled (0019): the Census 2022 NAICS list at levels 2 through 6 and the active four-character codes of GSA's Product and Service Codes Manual, April 2025, as CSVs inside the package, loaded by `orrery db migrate` and pointed at their `sources` row by `source_id`. The loader is an upsert that writes nothing when the store already holds the release's lists, so a refresh is shipping a new vintage rather than a user's chore, and one vintage of each is held at a time: mapping a code from one vintage to the next is a separate question and not answered here.

**Search layer (derived, rebuildable):**
- `notices_fts`: FTS5 external-content table over notice title + description, kept current by insert / update / delete triggers and rebuildable with `INSERT INTO notices_fts(notices_fts) VALUES ('rebuild')`. `orrery db reindex` rebuilds both FTS tables.
- `attachments_fts`: FTS5 external-content table over `attachments.extracted_text`, kept current by the same three triggers and rebuildable with `INSERT INTO attachments_fts(attachments_fts) VALUES ('rebuild')`. `orrery search` unions the two tables, takes the best-ranked hit per notice, and labels it with its source (the notice's own text or the attachment filename). Every front end reads through the query module (`src/orrery/query.py`), never these tables directly.
- `embeddings`: One row per embedded chunk of a notice description or an attachment's extracted text: `notice_id`, `attachment_id` (null for a description chunk), `chunk_index`, `page` (1-based, recovered from the form-feed page separators; null for descriptions), `text` (the chunk exactly as embedded), `model`, `vector` (float32 blob, stored raw), `created_at`; unique per (`model`, `notice_id`, attachment-or-0, `chunk_index`). Chunks are about 1,500 characters with 200 of overlap and never cross a page boundary. Written by `orrery embed`, which sends each pending source's chunks to the user's configured OpenAI-compatible embedding endpoint (`ORRERY_EMBED_BASE_URL`, default a local Ollama) and inserts them in one transaction per source, so a crash leaves nothing partial and the source is retried whole; an endpoint error ends the run. `orrery search --semantic` embeds the query the same way and ranks chunks for the configured model by sqlite-vec's `vec_distance_cosine`, best chunk per notice. Rebuild: delete the rows for a model and run `orrery embed` again; changing the model embeds into new rows and leaves old ones untouched.
- `notice_summaries` (0013): one row per attempt to summarize a notice on a chat slot: `notice_id`, the slot (`fast` or `deep`) and provider, the model, the prompt version, a hash of the rendered inputs, the tokens spent, the raw answer, the validated `result` as JSON (null when the answer failed validation), and its projections `summary` (two sentences), `work_type` (a fixed vocabulary), `keywords` (a JSON array of lowercase tags), and `stated_set_aside` (the set-aside the text itself states, as a SAM.gov code, for the many notices whose `set_aside_code` is empty). Written by `orrery summarize`, one row per notice per model and prompt version; a null-result row is recorded, never retried under the same model and prompt version. Rows are never updated (a trigger rejects `UPDATE`); a rebuild deletes a model's rows and runs `orrery summarize` again. No profile data goes in, so a summary serves every profile: the set-aside fit against the company profile is derived at read time, never stored.

**Views layer (read-only, interface version 1):**
- `v_notices`: every public notice column plus `agency` (the resolved entity's name), `agency_path_code` and `agency_path_name`, `url` (the SAM.gov page, from `raw_json`), `attachments`, `attachments_fetched`, `attachments_extracted`, and `versions`, and since 0007 the award fields a notice may carry as the source wrote them (`award_number`, `award_date`, `award_amount`, `awardee`, from the API's `award` object or the extract's award columns), and since 0013 the latest valid summary (`summary`, `work_type`, `keywords`, `stated_set_aside`, `summary_model`), and since 0015 the manifest state (`manifest_status`, `manifest_checked_at`), and since 0019 the code titles (`naics_title`, `psc_title`, left-joined from the reference tables so an unknown or retired code still reads).
- `v_notice_summaries` (0013): the latest valid summary per notice, whichever model wrote it, with its slot, model, prompt version, and time.
- `v_contractors`: one row per contractor entity with its keys, `awards`, `awards_value_usd`, and `last_award_date` from `contracts`, and `registration_status`, `registration_expires`, and `naics_primary` read from the latest fact of each predicate. Added by 0008.
- `v_contracts`: every contract column (since 0011 including `pop_potential_end`) plus `awarding_office` (the resolved entity's name, else the source's office name), `vendor` and `vendor_uei` (from the resolved entity, else the source's recipient fields), and `url` (the USAspending award page, from `raw_json`). Added by 0007.
- `v_entities`: every entity column plus `parent` (its name) and `notices`, the count of notices under the entity or any office below it.
- `v_pipeline`: tracked opportunities joined to their notice and agency, with `user_id` exposed for the consumer to filter and a `stage_order` for sorting. Private rows. Superseded by `v_pursuits` since 0010 and kept unchanged over the frozen legacy tables.
- `v_pursuits` (0010): every pursuit with its office and incumbent names, the incumbent's period-of-performance end, counts of linked notices and open tasks, the next task due, the next response deadline among its linked notices, and the last event time. `v_pursuit_tasks`: every task about a pursuit, with that pursuit's title, stage, and outcome. `v_tasks` (0018): every task whatever its subject, with the subject's display label and a `pursuit_id` that is null for every other subject, so a consumer wanting pursuit work alone can filter on it without knowing the vocabulary. Private rows.
- `v_quota_daily`: keyed SAM.gov requests and failures per UTC day.
- These views are the stable interface for community dashboards (Datasette, Grafana, scripts) and what the engine's own detail reads use, so the test suite exercises them. Stability rule: columns are only ever added; a column that must be renamed or change meaning arrives under a new view name, and the old view stays until the next major version. Interface version 1 was created by migration 0006 and extended, columns and views only added, by 0007, 0008, 0013, 0015, 0018, and 0019.

**Workspace layer (user data -- kept strictly separate from public data):**
- `users`: Present from day one even though v1 is single-user. Columns: `user_id`, name, `created_at`; seeded with user 1, `local`.
- `workspace_documents` (0009): the user's documents as written, in TOML: `user_id`, `kind` (`profile` or `workflow`), `version`, `body`, `created_at`; unique per user, kind, and version; append-only by trigger. Every save is a new version, so an assessment can cite the profile it was made against and a workflow change never rewrites history. The typed `company_profiles` columns below are a projection of the latest profile document. The workflow document lists the shop's stages in order, each with a key, a name, the gate its work feeds (none for a stage with no decision at its end), and the tasks a pursuit starts with on entering it; the default is streamlined Shipley (identify → Pursuit Gate, qualify → Capture Gate, capture → Bid Gate, proposal → Bid Confirmation Gate, submitted, post-award) and `orrery workflow edit` replaces it. Saved searches are not documents, but `orrery searches edit` presents one as TOML and re-saves it through the same replace-by-name path.
- `company_profiles`: The user's own company, one row per `user_id` (the primary key): name, UEI and CAGE (which will link it to its own public entity row when source 3 lands), NAICS list, socioeconomic certifications (JSON array of codes such as SB, SDVOSB, WOSB, HUBZone, 8(a)), capability statement text, target agency path prefixes, `updated_at`. List columns are JSON arrays in TEXT, checked as arrays, read with `json_each`. Since 0009 the row is a projection of the latest profile document: `orrery profile edit` opens the document as TOML in `$EDITOR` (or takes `--file`), validates it against a model that forbids unknown keys, stores it as the next version, and overwrites these columns from it (NAICS from offerings, certifications from qualifications, target prefixes from markets) in one transaction. The document has sections for the company, offerings, markets, qualifications, competitors, partners, and notes for AI; it is the input that makes fit scoring, gap analysis, and PWin judgment possible, and the version an assessment cites.
- `company_past_performance` (later, §9 step 6): `user_id` FK; one row per contract the company has performed: `contract_id` where it resolves to a public award, otherwise free text; customer entity, value, period, relevance notes.
- `company_partners` (later, §9 step 6): `user_id` FK; teaming partners and competitors of interest, each linked to a public `entity_id` where known, with a relationship type and notes.
- `pursuits` (0010): the unit of BD work, anchored on a requirement rather than a notice: title, summary (the need in the user's words), the buying office (`office_entity_id` where resolved and the office code kept beside it), NAICS, the incumbent `contract_id`, `stage` (a key of the workflow document), PWin, notes, `held_until` while parked at a gate, `outcome` (`no-bid`, `lost`, `won`), `closed_at` (open while null), timestamps. Never deleted: a dropped pursuit is closed `no-bid`, and may be reopened. Migration 0010 turned every tracked opportunity into a pursuit with the same id (watching → identify, pursuing → qualify, bid → proposal, submitted → submitted, won → post-award with outcome won, lost and no-bid closed with their outcome), linked its notice, and copied its events; the `tracked_*` tables stay, frozen.
- `pursuit_notices`: the notices a pursuit collects, each with a role (solicitation, rfi, sources-sought, presolicitation, amendment, award, other). Government dates are read from here and from the incumbent contract at query time, never copied, so an amendment's new deadline shows up without anyone touching the pursuit.
- `tasks` (0018, was `pursuit_tasks`): the user's work, one row per task. The subject is polymorphic in the style `facts` uses -- a `subject_type` of `pursuit`, `entity` or `person` with a `subject_id`, both null together for a standalone to-do -- so a task may be about an office or a point of contact and not only about a pursuit. `requirement` joins the vocabulary when a requirement becomes writable. Referential integrity is given up for that, and replaced by one write-time resolver in `workspace.py` that every insert goes through; the check is asymmetric on purpose, since a pursuit is the user's own row and an entity or person is a public one with no `user_id` to match. `stage` is a key of the workflow document and null outside a pursuit's workflow. `origin` is `template` (seeded on entering the stage), `user`, or `alert` (emitted by a rule; nothing emits yet). `precedence` is the FLASH / IMMEDIATE / PRIORITY / ROUTINE scale, assigned by the user and stored rather than derived; null means the user has not said, which is not a fifth level and not a synonym for ROUTINE. A task that is not about a pursuit writes no `pursuit_events` row -- that log is pursuit-scoped -- so its history is its `created_at` and `done_at` and nothing more, until alert provenance fills the gap. Suggested tasks a user accepts from an assessment are `user`, not `alert`: a suggestion a human accepted is the user's own work, and `alert` belongs to rules.
- `pursuit_events`: append-only by trigger: every stage change, gate decision (go, no-go, hold) with its rationale, PWin and notes change, task completion, notice link, close, and reopen.
- `assessments` (0012): AI assessments of a pursuit, append-only by trigger, each carrying the provenance an assertion needs: the slot (`fast` or `deep`) and provider, the model, the prompt version, the profile document version it cited (null when none existed), a hash of the rendered inputs, the tokens spent, the raw answer, and the validated result as JSON. Read only through `workspace`; the latest one rides on the pursuit detail.
- `saved_searches`: `user_id` FK; named query definitions, unique per (user, name): optional FTS5 `query` text plus structured filters, each nullable meaning "any": `naics` and `set_asides` (JSON arrays of codes), `agency_path_prefixes` (JSON array of `full_parent_path_code` prefixes matched on dot boundaries), `deadline_within_days`. Running one applies the filters as predicates over active notices and, when `query` is set, intersects with the keyword search ranked by bm25; otherwise it lists by soonest deadline. The structured filters (not the text) also drive fetch priority: a pending description or attachment whose notice matches any user's saved search is fetched before the rest. The future alerting primitive. Rows are the user's own and may be updated or deleted.
- `tracked_opportunities`: `user_id` FK; the user's pipeline, one row per (user, notice): stage (watching / pursuing / bid / no-bid / submitted / won / lost), current pwin (0 to 100), notes, `created_at`, `updated_at`. Never deleted: a dropped pursuit is `no-bid`. Tags arrive with the `tags` tables (later).
- `tracked_opportunity_events`: Append-only log of every change to a tracked opportunity: `tracked_id`, `user_id`, `changed_at`, field (stage / pwin / notes), old value, new value (null old value on first sight). Written in the same transaction as the change; triggers reject `UPDATE` and `DELETE`. PWin trajectory is intelligence by the same argument that justifies `notice_versions`.
- `tracked_entities` (later, §9 step 6): `user_id` FK; agencies, contractors, and officials the user follows, which also drive adapter slice selection for sources 3 and 4.
- `tags`, `tracked_opportunity_tags` (later, §9 step 6): Freeform organization; `tags` carries a `user_id` FK.

**Design rules:**
- Raw + typed ("ELT") pattern: always keep `raw_json`; typed columns are a parse that can be re-run when the parser improves.
- All timestamps are text in ISO-8601 UTC, `YYYY-MM-DDTHH:MM:SSZ`. Natural keys from the source where stable (`notice_id`, `uei`, `piid`).
- Schema changes are numbered SQL files in `src/orrery/migrations/`, applied in order by `orrery db migrate`, each inside one transaction, and recorded in `schema_migrations` (name, `applied_at`), which the migrate command creates itself.
- Workspace rows are the user's own data and, unlike the ingestion layers, may be updated and deleted, with two exceptions: `tracked_opportunities` rows are never deleted, and `tracked_opportunity_events` is append-only. Every workspace query filters by `user_id`. The `priority` column of `attachments` from migration 0001 was never written and was dropped in 0005; fetch priority is computed at queue time from saved searches.
- Every ingested row resolves to an entity by exact key or records an unresolved alias. Resolution is never silent and never destructive; a wrong merge is undone by re-resolving the aliases.
- Every fact names its source. Rows in `facts` are append-only and are never updated in place.
- Nothing in the identity or ingestion layers is deleted. When a notice stops appearing in the API or the active extract, `active` goes false and `last_seen_at` stops advancing; the row, its versions, and its attachments persist. In v1 the flag is cleared by a complete pass of the active extract, only for notices whose NAICS is in the configured slice, by comparing `last_seen_at` with the extract's own `source_generated_at` (§8) -- when the file was cut, not when the run reading it began. The distinction is the whole of it: the file is a snapshot taken earlier in the day, so a notice the keyed API ingested after the cut is absent from it for that reason alone and is not evidence of anything. A pass that cannot establish the cut clears nothing and says so, rather than falling back to a time that would deactivate live notices.
- Public/ingested tables are world-shareable; workspace tables are private and every workspace row carries a `user_id`. This boundary is what makes a future hosted deployment possible without a rewrite.
- Derived layers (FTS, embeddings, trends) must be rebuildable from ingestion tables at any time.
